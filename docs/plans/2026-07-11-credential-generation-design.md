# 证件审批、制证与发放闭环设计

## 目标

补齐当前断在 `approved` 的证件流程，使赛事管理员能从应用层完成：

```text
申请 submitted
  -> 审批与首次制证（同一事务）
  -> 请求 generated + 证件 generated
  -> 人工发放
  -> 证件 issued
```

审批拒绝仍进入 `rejected`，不创建证件。

## 选择

采用“审批即制证”。当前系统没有独立制证页面、接口或后台任务；发放页面只处理已经存在的 `generated` 或 `printed` 证件。把首次制证放入审批事务，可以直接接通现有页面，同时避免新增一套悬空状态。

未采用：

- 人工点击制证：需要新增页面、权限和 API，当前没有对应操作岗位。
- 异步批量制证：需要任务状态、失败重试和批次运维，不适合先修复单条业务闭环。

## 事务与数据流

审批通过时，在一个数据库事务中：

1. 锁定并校验请求属于当前组织和赛事，状态只允许 `submitted`、`under_review` 或 `approved`。
2. 校验最终类别和通行区域。
3. 检查该请求是否已有证件；已有则拒绝重复制证。
4. 更新请求审核字段，并把请求状态设为 `generated`。
5. 生成赛事内递增的 `CRED-xxxxxx` 证件号。
6. 创建 `generated` 证件，复制申请人、单位、类别、颜色、职务和最终通行区域。
7. 生成包含证件 ID、证件号、赛事、组织和版本的签名二维码。

任一步失败，审核更新和证件创建全部回滚。

## 权限边界

- `race_admin`、`org_admin`、`super_admin`：查看请求、审批、查看待发放证件与统计、执行发放。
- `org_admin`、`super_admin`：作废和补办。
- 所有动作继续经过赛事访问校验；只读赛事权限不得写入。
- 应用层仍要求 `app:credentials` 模块，管理层仍要求 `admin:credentials` 模块。

## 错误与防重

- 重复审批已生成请求：返回 400，不创建第二张证件。
- 证件号冲突：事务失败并回滚；由唯一约束阻止重复记录。
- 类别或区域不属于当前赛事：返回 400。
- 请求、证件跨组织或跨赛事：返回 404/403，不泄漏其他租户数据。
- 发放已发放或已作废证件：返回 400。

## 验收样例

自动化测试必须证明：

1. 赛事管理员创建请求后，状态为 `submitted`。
2. 审批通过返回 `generated`，并带有 `credentialId` 和 `credentialStatus: generated`。
3. 列表接口能看到唯一一张待发放证件，类别和通行区域与审核结果一致。
4. 再次审批同一请求失败，证件数量仍为 1。
5. 发放后证件状态为 `issued`，发放日志存在。
6. 审批事务中人为制造制证失败时，请求仍保持原状态。
7. 浏览器从申请页建单，经审核页通过，再到发放页完成领取；全程无 4xx/5xx、资源失败或页面异常。
